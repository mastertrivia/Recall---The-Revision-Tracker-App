# F. v4.11 — Display Size Root Cause, Top-Bar Removal, App & Data Menu, Fail-Safe Backups

Date: 2026-10-23. Companion to the GT-01..GT-07 timer audit (docs 01–05).

## 1. The Display Size defect and its root cause

**Symptom (reported on device, twice):** enlarging the UI above the normal size worked
(levels 7–10, and earlier Medium → Large), but every request to make it *smaller*
(levels 1–5, and earlier Small / Extra Small) produced essentially zero visible change.
The same asymmetry survived two implementations of the setting (4-size → 1–10 levels),
which pointed at the architecture rather than the picker.

**Investigation:**

1. The real `index.html` was run in Chromium with mobile emulation
   (`tests/viewport-render.test.js`): the *exact shipped meta strings* shrink and enlarge
   correctly in every direction (level 5 → `vv.scale=0.926`, level 1 → `0.681`,
   level 10 → `1.36`), and a raw-document probe proved no ingredient of the meta string is
   at fault. So the HTML engine and its math were sound.
2. Android's documentation states: *"When your page is rendered in a WebView, it doesn't
   use wide viewport mode by default"* — `WebSettings.setUseWideViewPort()` and
   `setLoadWithOverviewMode()` both default to **false**, and this wrapper never set them.
   Chromium's own `android_webview/docs/web-page-layout.md` calls
   `setUseWideViewPort(true)` + `setLoadWithOverviewMode(true)` the **"configure WebView
   like a browser"** setup (the System WebView Shell ships with exactly that).
3. In narrow viewport mode the meta `width` is ignored and overview/zoom-out — what a
   sub-1.0 scale *is* — is disabled; zoom-in above 1.0 is not gated. That reproduces the
   observed asymmetry exactly, explains why the old 4-size implementation failed the same
   way (same meta pipeline), and why the system Display size setting (a density change
   *below* the WebView layer) still shrank the app.

**Fix (one mechanism, no double scaling):**

- `MainActivity.configureWebView`: `useWideViewPort = true`, `loadWithOverviewMode = true`
  with a comment documenting the root cause. Level 6 still writes the stock
  `width=device-width, initial-scale=1.0` meta → byte-identical baseline (asserted by
  `tests/display-size.test.js` DS2.2).
- Wrapper otherwise unchanged: `textZoom` pinned to 100 (re-pinned on config change),
  level persisted natively (`getDisplayScale`/`setDisplayScale`, default `2`,
  legacy migration).
- On-device debug readout added to the Display Size card (kept permanently by request):
  level → scale → meta → `innerWidth`/`vv.scale` (+ `applied ✓` / `NOT APPLIED ✗`) →
  native settings. Its native line reads **main-thread-cached** values because
  `getDiagnostics()` runs on the JS bridge thread and direct WebView reads from there
  failed silently on device (returned placeholder values).

**Evidence:** display-size suite 60/60, viewport-render phases 1–3 all correct,
device screenshots at levels 1/2/3/6/7–10 confirmed progressive shrink/enlarge with
`vv.scale == scale`.

## 2. Top-bar removal + App & Data menu

- Theme `Theme.GoalTracker` → `Theme.AppCompat.DayNight.NoActionBar`; `main_menu.xml`
  deleted along with `onCreateOptionsMenu`/`onOptionsItemSelected` and the menu strings.
  The HTML now starts directly under the status bar.
- Every former menu item was re-homed as a bridge method that opens the **same native
  typed-confirmation dialog and file picker** (so HTML-triggered actions keep the native
  lock-out protection — a broken HTML can still only open validated native flows):
  `refreshApp`, `importHtmlFile`, `exportCurrentHtml` (new capability: saves the
  *currently running* index.html, custom installs included), `factoryResetUserData`,
  `systemCheck`; `exportBackup`/`importBackup` now show their dialogs first.
- HTML: new **App & Data** card (first card of Android Shell Settings) with the seven
  rows in the exact specified order and renames; the Backup card and the HTML App
  Management card were removed (no duplicated entries); Diagnostics keeps Error Log only
  (System Check moved to the menu). The Android Shell Settings launcher moved to the
  **top** of the Settings list.
- Removed as requested: "Restore Default App" menu item. Guarantees preserved:
  installing HTML never deletes user data (staged validation, existing code path);
  Factory Reset never touches `appDir` (existing `factoryReset()` behavior, now behind
  a dialog titled "Factory Reset User Data").

## 3. Fail-safe backup pipeline

**Old failure mode:** `restoreBackupFrom` checked only the `app` field, then wrote *every*
value blindly; the HTML side cleared IndexedDB **before** inspecting the snapshot — so a
corrupt/foreign file could wipe real data or leave garbage state that rendered as
"random text".

**Native gate (`BackupValidator`, pure Kotlin, 13 JUnit checks):** full JSON parse →
`app == "goal-tracker-shell"` → every value must be text and JSON-looking values must
parse → `gt_backup.state.settings` must exist → `tasks`/`sessions`/`timeline` must be
arrays → FNV-1a checksum (present on new exports) must match. Only then are files staged
to a temp dir and swapped in. Rejections surface as `Import failed: <reason>` and touch
nothing.

**Export:** fresh mirror first (the HTML aborts the export if the mirror cannot be read),
checksum computed over sorted keys, refuses to export with no `gt_backup`, `saveData`
writes are now temp-then-rename (no torn reads by a concurrent export).

**HTML gate (`gtValidateSnap`, 10 matrix checks):** the snapshot is validated *before* any
`idbClear`; a mid-restore failure rolls the database back to the in-memory copy taken at
start, and every failure path says `Import failed: …`.

**Evidence:** `tests/backup-robustness.test.js` 51/51 (menu structure/order/dispatch,
mirror freshness, corrupt/foreign rejection without data loss, valid full restore),
`BackupValidatorTest` in `gradlew test`.

## 5. Known limitations

- Android cannot expose the "natural" density behind a system Display-size override, so a
  *system* density change still shifts the base size slightly (relative levels stay exact);
  documented in the settings copy as "as far as the platform permits".
- On phones narrower than ~350 CSS px, level 10 degrades gracefully (slightly less than
  1.36) instead of clipping — by design, covered by the zoom-invariant test floor.
- Backups created before v4.11 carry no checksum; they still pass the full shape gate
  (checksum check is skipped only when the field is absent).
